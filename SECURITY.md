# Security Policy

## Reporting Security Issues

If you discover a security vulnerability in WriteHERE, please report it by emailing the maintainers. **Do not create public GitHub issues for security vulnerabilities.**

## Security Best Practices

### API Key Management

1. **Never commit API keys to version control**
   - Use `.env` files for local development (already gitignored)
   - Use environment variables in production
   - Rotate keys regularly

2. **File permissions**
   - Set restrictive permissions on `api_key.env`: `chmod 600 recursive/api_key.env`
   - Ensure backend temporary key files are not world-readable

3. **Production deployment**
   - Use a secrets management service (AWS Secrets Manager, HashiCorp Vault, etc.)
   - Never use the development server in production
   - Use proper WSGI server (gunicorn with eventlet)

### CORS Configuration

The default CORS configuration allows `localhost:3000` and `localhost:8000` for development.

**For production**, set the `ALLOWED_ORIGINS` environment variable:

```bash
export ALLOWED_ORIGINS="https://yourdomain.com,https://www.yourdomain.com"
```

### SSL/TLS

SSL verification is enabled by default for all HTTP requests. Only disable it in development if absolutely necessary:

```bash
export DISABLE_SSL_VERIFY=true  # Development only!
```

### Serialization Security

The project uses `dill/pickle` for serialization, which can execute arbitrary code. **Never load pickle files from untrusted sources.**

- Only load `.pkl` files generated by your own application
- Path validation is enforced to prevent directory traversal
- Consider migrating to JSON-based serialization for better security

### Running in Production

1. **Disable debug mode**
   ```bash
   export FLASK_DEBUG=false
   ```

2. **Use a production-grade WSGI server**
   ```bash
   gunicorn --worker-class eventlet -w 1 --bind 0.0.0.0:5001 backend.server:app
   ```

3. **Set allowed origins**
   ```bash
   export ALLOWED_ORIGINS="https://yourdomain.com"
   ```

4. **Use HTTPS**
   - Always use HTTPS in production
   - Configure proper SSL certificates
   - Use a reverse proxy (nginx, Apache) for SSL termination

## Known Security Considerations

1. **Pickle deserialization**: The application uses `dill/pickle` for state persistence. This is inherently unsafe if loading untrusted data. Future versions should migrate to JSON.

2. **Process termination**: The task stopping mechanism searches and kills processes. While sanitized, it should only be exposed to authenticated users in production.

3. **File operations**: Backend creates temporary files for tasks. Ensure proper file permissions and cleanup.

## Security Updates

